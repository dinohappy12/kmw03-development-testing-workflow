# 任務依賴、重現與根因定位

## 拆的是可驗收成果
簡單修正直接實作，不建立任務系統。跨模組需求才用短表：編號／前置／本步可用成果／完成條件／驗法／狀態／證據。每步走通一條窄但完整的使用路徑，避免先寫完全部 UI 才處理資料與驗證。

例如「上傳舊 ZIP，替換一支 Skill，其餘保留」：
1. A：讀舊包並列出內容，拒絕缺必要主檔的包；無前置。
2. B：使用新 Skill 合併，展示其他檔案位元組不變；前置 A。
3. C：輸出新包並重新讀取，比對 manifest／版本／必要檔與差異；前置 B。
4. D：實際帳號上傳、新對話與手機使用；前置 C，無帳號工具則明列待測。

每步的案例由規格決定。A 完成才開始 B；C 本機通過不代表 D 完成。不為了拆任務額外發 GitHub Issues。真要使用議題追蹤時先確認使用者自己的目標 repo，不能把學員的工作發到第三方工具作者的倉庫。

若為廣泛更名或資料結構遷移，可採「新增兼容形式→分批遷移→驗證→移除舊形式」，每批保留可用狀態；不要硬拆成會讓主線暫時壞掉的小步。不要因來源慣例任意重命名現有專案文件或識別碼。

## 除錯是縮小可驗證問題
1. 收集原始輸入、環境、版本、實際與預期。機密先遮蔽；不把憑證寫進指令或公開證據。
2. 找最便宜且能打中症狀的入口：既有測試、CLI、小型 HTTP 請求或瀏覽器。確認失敗是使用者描述的那件事；只「沒有報錯」不夠。
3. 縮減到仍能重現的案例，保留原案例。不能重現時記錄已試入口與缺少的環境／去識別資料，不編造根因。
4. 有多個合理原因才排序假設，寫「若原因 X，改變 Y 應得到 Z」。一次探測一個變因；效能問題先量基準，不能憑感覺說變快。
5. 在能觸發原問題的接口保存回歸案例，先確定它會失敗，再作最小修正。若必須重寫測試，先說明測試是否違反規格，不能為綠燈放寬完成條件。
6. 重跑該案例及受影響檢查；必要時回到原始完整案例。整理暫時診斷記錄，交根因、差異及證據。

偶發問題只在既定預算內取少量固定種子／可重播樣本；不直接採用來源的數百次或無限壓力迴圈。預算用完保留重現資料與下一步；新迴圈不得繞過原 state。需要登入、手機或宿主功能才看得到的錯誤，交最少人工操作，不用本機替身宣稱真實平台通過。

## 交付、審閱與復盤
比較修改前固定基準與本輪結果，需求、專案規則分開審閱；來源缺失標待確認。同 AI 依序檢查不叫獨立審查。

交付用最小流程圖＋修正前後證據＋受影響範圍＋還原方式。對可逆性分清「可還原檔案」與「已發訊息、對外交易等不可自動撤回動作」。完成條件通過後停止新增推測性測試。

有真實失敗才復盤：找檔繞路可加精確入口；原有檢查沒接上先接既有檢查；固定錯誤才補確定性檢查；美感／語氣問題留人工判準。提出改善與已執行修改分開，不自動改全域 AGENTS、安裝框架或無限自我修訂。
